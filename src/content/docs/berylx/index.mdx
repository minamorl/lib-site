Order #4127 reserves **2 units at tokyo-2** while its risk score is calculated. The card then declines. The recovery handler needs those exact reservation details: clear the held stock, record the failure, and stop before notifying the customer.

`berylx` composes named tasks over one immutable state. `then` passes successful state forward. `par` runs branches from the same snapshot and merges their changes. A `catch` receives the state at the failed node. Here, `release` handles the failure and returns another `Err`, so `notify` never runs.

  code={recovery}
  lang="ts"
  title="Your recovery handler, with the state it needs"

**This is an executable in-memory example.** The service steps are deterministic stand-ins; no inventory or payment API is called. Clearing a field does not cancel a real reservation. External compensation, including failures while compensating, is application code. Keeping committed state unchanged does not undo side effects.

| Responsibility        | By hand in this example                                     | With berylx in this example                                               |
| --------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------- |
| Join the branches     | Pick `stock` from one result and `risk` from the other.     | `par` compares each branch with the common base and merges changed paths. |
| Preserve failed state | Keep `current` in a closure, then attach it to an error.    | `Err.focus` carries the partial state into the `catch` handler.           |
| Commit on success     | The function reaches `committed = current` only on success. | With the async runner, explicitly guard `root.commit` with `Ok`.          |

Object spread is fine for patches with known ownership. It is **not a three-way merge of whole snapshots**: `{ ...left, ...right }` can replace a changed `stock` with the other branch's untouched copy. The full file demonstrates that pitfall separately before doing the join correctly.

<Act
  number="04"
  kicker="choose the abstraction you need"
  title="Where berylx fits."
  id="compare"
/>

These libraries solve different problems. The comparison below is about **how our checkout examples are written**, not a claim that another library cannot express the same behavior.

|                      | What you compose                                             | How this checkout keeps recovery state                                                              | Choose it for                                                                      |
| -------------------- | ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| **berylx 0.3.0**     | Named tasks, `then`, `par`, and `catch`.                     | `Err.focus`, provided to the catch handler.                                                         | An inspectable workflow over one state object, with a defined merge law.           |
| **Effect 3.22.2**    | Effects with typed success, error, and environment channels. | This sample uses `Ref` and a typed `CheckoutFailed` error; immutable values are another option.[^1] | A broader effect system with structured concurrency, services, and scheduling.[^2] |
| **XState 5.33.2**    | States, events, transitions, and actors.                     | Context at the `onError` transition.[^3]                                                            | Event-driven behavior, explicit statecharts, and actor inspection.[^4]             |
| **neverthrow 8.2.0** | `Result` / `ResultAsync`, `andThen`, and `orElse`.           | This sample closes over state, then places it in `CheckoutFailed`.[^5]                              | Typed success and failure values with a small composition surface.                 |

All five implementations check the **same accepted-card and declined-card results**, using the shared fixture and async execution. They are illustrative implementations, not minimal programs, benchmarks, or a proof of equivalent behavior for every failure. Validation and other untested failures may differ. No line-count ranking is used.

berylx runs **inside your process**. It does not provide durable execution, a scheduler, or a retry policy. If workflows must survive process loss, a durable platform such as [Temporal](https://docs.temporal.io/evaluate/understanding-temporal) addresses that different requirement.

`dryRun` is a **structural traversal, not a payment simulation**. Task bodies become successful identity operations. It therefore lists `notify` and skips the catch handler even for the declined-card input. Branch predicates are evaluated against the supplied state; task updates and failures are not predicted.
